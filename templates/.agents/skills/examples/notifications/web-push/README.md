# Web push notifications (browser-native, works when app is closed)

**When to copy this example:** the user wants to send notifications
that show up even when the user doesn't have the tab open. Different
from `notifications/in-app-notifications/` (which is the bell-and-feed
inside the app).

## What you'll install

```bash
cd /workspace
npm install @molecule/api-push-notifications @molecule/api-push-notifications-web-push --workspace=api
```

The app-side component (`EnablePushButton.tsx`) uses the browser Push API directly — no extra app package needed.

## Files in this example

| Path                                  | What it does                                                                                                                                                                        |
| ------------------------------------- | ----------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| `api/bonds/push-web-push.ts`          | Calls `setProvider(provider)` from `@molecule/api-push-notifications` to wire the web-push implementation.                                                                          |
| `api/handlers/push.ts`                | `GET /push/public-key` returns the VAPID public key (503 until configured) so the client can subscribe; `POST /push/subscribe` saves the subscription; `POST /push/test` sends one. |
| `app/components/EnablePushButton.tsx` | Asks browser for permission, registers the service worker, posts the subscription to the API.                                                                                       |

## Receiving pushes (the service worker)

There is no `sw.ts` to copy. The app's service worker is generated by
**vite-plugin-pwa** (Workbox `generateSW`) — that generated `/sw.js` is the one
`EnablePushButton.tsx` registers. It ships **no `push` listener**, so a delivered
push displays nothing until you add one. Don't hand-write a second `/sw.js`; it
would clash with the generated worker. Instead ship a dependency-free handler and
pull it into the generated worker via Workbox `importScripts`.

Add `app/public/push-sw.js` (the API sends the `@molecule/api-push-notifications`
`{ title, options }` payload, so read those fields):

```js
// push-sw.js — imported into the generated Workbox worker
self.addEventListener('push', (event) => {
  let payload = {}
  try {
    payload = event.data ? event.data.json() : {}
  } catch (_error) {
    // Non-JSON body → degrade to plain text as the title.
    payload = event.data ? { title: event.data.text() } : {}
  }
  if (!payload.title) return
  event.waitUntil(self.registration.showNotification(payload.title, payload.options || {}))
})

self.addEventListener('notificationclick', (event) => {
  event.notification.close()
  const data = event.notification.data || {}
  const href = typeof data.href === 'string' ? data.href : '/'
  event.waitUntil(
    self.clients.matchAll({ type: 'window', includeUncontrolled: true }).then((clients) => {
      const client = clients[0]
      return client ? client.focus() : self.clients.openWindow(href)
    }),
  )
})
```

Then pull it into the generated worker from the PWA plugin's Workbox options in
`vite.config.ts`:

```ts
VitePWA({
  // ...existing options
  workbox: { importScripts: ['push-sw.js'] },
})
```

## Required env

```
VAPID_PUBLIC_KEY=...
VAPID_PRIVATE_KEY=...
VAPID_EMAIL=mailto:you@example.com   # the bond reads VAPID_EMAIL, not VAPID_SUBJECT
```

Generate with `npx web-push generate-vapid-keys`.

## Anti-patterns

- Do not request push permission on page load. Users decline by
  reflex. Ask after a meaningful interaction (e.g. they enable
  notifications in settings).
- Do not invent `@molecule/api-push` or `@molecule/api-fcm` — the
  core package is `@molecule/api-push-notifications` (use its `send()`)
  and the provider is `@molecule/api-push-notifications-web-push`.
- Do not use `bond('push', provider)` — wire with `setProvider(provider)`
  from `@molecule/api-push-notifications`.
- Do not read the VAPID public key from a `window` global or a build-time
  constant. The browser needs it as `applicationServerKey`, but nothing sets
  such a global. Serve it from `GET /api/push/public-key` (the public key is
  public by design — it ships in every push request) and `fetch` it right
  before `pushManager.subscribe()`, exactly as this example does. NEVER expose
  `VAPID_PRIVATE_KEY` to the client.
- Do not hand-write your own `/sw.js` — vite-plugin-pwa already
  generates it. Add push handlers via `workbox.importScripts`
  (see "Receiving pushes" above), never by replacing the worker.
- Do not send marketing-style pushes. Browsers blacklist apps
  that abuse the API.
- Do not forget to handle 410 Gone responses from the push
  service — that means the subscription is dead, delete it from
  your DB.

## Verify

User clicks Enable in settings → browser shows permission prompt
→ accept → subscription saved → admin sends "Test push" → user
sees a system notification even with the tab closed.
